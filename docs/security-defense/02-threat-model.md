# 威胁模型与分层防御

> 本文档定义 blog-lite 面临的威胁分层，以及每一层防御的责任边界。
> 这是设计决策的依据：每一层该挡什么、挡不了什么、为什么不能替代。

---

## 1. 核心认知：为什么必须分层

**单层防御必然失效**，因为不同防御层的能力边界是硬性的：

| 防御层 | 擅长 | 做不到 | 原因 |
|---|---|---|---|
| nginx | 按频率/IP 拒绝洪水 | 理解业务语义 | 高性能建立在"不懂业务"之上 |
| 应用层 | 按 userId/行为识别滥用 | 扛住流量洪水 | 单进程，洪水进来自己先挂 |
| CDN/CF | 挡大流量/分布式攻击 | 细粒度业务判断 | 在边缘，看不见回源后的业务 |

**这不是"谁强谁弱"，是分工不同。** nginx 性能高是因为它简单，应用层不可替代是因为它懂业务。防御是漏斗，每一层过滤不同的威胁。

---

## 2. 威胁分层与防御责任

按"博客项目实际可能遇到的"威胁，由高到低分层：

### Tier 1：纯流量洪水（L4/L7 flood）— nginx + CDN 挡

| 特征 | 每秒上万请求，打满带宽/CPU/连接 |
|---|---|
| 谁能打 | 专业攻击团队、booter 服务、反射放大 |
| 应用层能挡吗 | ❌ 自己先挂 |
| nginx 单机能挡吗 | ⚠️ 4H4G 撑到 3-5w rps，再高挂 |
| 正解 | **CDN（Cloudflare 免费版 L7 DDoS 缓解）+ Under Attack 急救** |
| 博客遇到概率 | 极低（不值得被这样针对）|

### Tier 2：中等强度 HTTP flood — nginx 主力

| 特征 | 每秒几千请求，单 IP 或少量 IP 暴力跑 |
|---|---|
| 谁能打 | 稍有技术的攻击者、租来的 VPS |
| 应用层能挡吗 | ❌ 勉强，但每个请求都消耗资源 |
| nginx 能挡吗 | ✅ `limit_req` + IP 黑名单，挡在应用前 |
| 正解 | **nginx limit_req_zone + lua 黑名单（应用层下沉的 IP）** |

### Tier 3：慢速分布式刷（CC）— 应用层主战场

| 特征 | 代理池轮换 IP，每 IP 频率正常，但登录同一账号狂刷 |
|---|---|
| 谁能打 | 小型黑产、有代理池资源的攻击者 |
| nginx 能挡吗 | ❌ 每个 IP 频率都正常，看不出异常 |
| 应用层能挡吗 | ✅ 按 userId 聚合，识别"同一账号跨 IP 刷" |
| 正解 | **userId 维度限流（P0 修复后生效）+ 失败熔断** |

### Tier 4：有效 token 穷举爆破（最难防）— 应用层 + 业务设计

| 特征 | 攻击者有合法 token，脚本狂试兑换码/密码 |
|---|---|
| 谁能打 | 拿到 token 的任何人（注册账号或窃取 token）|
| nginx 能挡吗 | ❌ 请求和正常用户长得一样 |
| CF Under Attack 能挡吗 | ❌ 能过 Challenge 拿到 cookie 后，脚本和真人无异 |
| 应用层能挡吗 | ⚠️ 能识别（按 userId + 失败次数），但**必须进应用才能判断** |
| 正解 | **失败熔断（连续失败自动拉黑）+ 凭证强度（兑换码足够长）+ 单设备登录（防 token 窃取）** |

### Tier 5：脚本小子（curl/requests）— CF 就挡死

| 特征 | 单机脚本，无浏览器环境 |
|---|---|
| 谁能打 | 任何人 |
| CF Under Attack 挡吗 | ✅ JS Challenge 直接挡死（脚本过不了）|
| 应用层挡吗 | ✅ 限流轻松挡 |
| 正解 | **CF 常态防护 + 应用层限流** |

## 3. 关键攻击场景分析

### 3.1 场景：代理池刷会员兑换码

```
攻击者用 1000 个代理 IP，每个 IP 每秒 2 次请求（远低于限流阈值），
全部登录同一账号 A，狂试兑换码。
```

| 层 | 能否识别 | 原因 |
|---|---|---|
| nginx | ❌ | 1000 个 IP 每个每秒 2 次，全部正常 |
| CF | ❌ | 能过 Challenge（用了无头浏览器）|
| 应用层（现状）| ❌ | userId 维度限流没生效（缺陷 1）|
| **应用层（P0 修复后）** | ✅ | userId A 1 分钟试了 6000 次 → 立刻 429 |
| **应用层（P1 熔断后）** | ✅ | 连续失败 20 次 → 自动拉黑 + 下沉 nginx |

**结论：这个场景只有应用层能管，P0 + P1 修复后闭环成立。**

### 3.2 场景：有效 token + 慢速刷（卡在阈值内）

```
攻击者有合法 token，每分钟只刷 9 次（低于 10 次限流），
但持续 24 小时慢速爆破兑换码。
```

| 层 | 能否识别 | 原因 |
|---|---|---|
| 限流 | ❌ | 频率在阈值内 |
| **失败熔断（P1）** | ✅ | 兑换码连续失败累计 → 达阈值拉黑 |
| 凭证强度 | ✅ | 兑换码 8 位以上混合字符，爆破空间够大 |

**结论：限流挡不住"阈值内慢刷"，必须靠失败熔断 + 凭证强度。**

### 3.3 场景：大流量 flood（10w+ rps）

```
专业攻击，每秒 10 万请求打过来。
```

| 层 | 能否扛住 | 原因 |
|---|---|---|
| 应用层 | ❌ | 秒挂 |
| nginx 单机（4H4G）| ❌ | 撑到 3-5w rps，再高挂 |
| **CDN（Cloudflare）** | ✅ | 边缘节点接收，回源的是干净流量 |
| **Under Attack 模式** | ✅ | 急救，临时开启 |

**结论：10w rps 必须靠 CDN。但这不是应用层文档的范畴，本文档不展开。**

## 4. Cloudflare 的定位（明确边界）

### CF 能做什么
- **免费版 L7 DDoS 缓解**（always on，零成本）：挡 Tier 1 大流量
- **Managed Challenge / Turnstile**：JS Challenge 挡 Tier 5 脚本小子
- **Under Attack 模式**：急救包，被攻击时临时开，挡洪水 + 增加脚本门槛
- **Rate Limiting 规则**：IP 维度补充限流（免费有额度）

### CF 做不了什么（关键认知）
- ❌ **挡不住有效 token 慢速刷**：能过 Challenge 拿到 cookie 后，脚本和真人无异
- ❌ **看不见 userId**：在边缘，解不了 token，做不了业务级判断
- ❌ **不能替代应用层限流**：CF 限流是 IP 维度的，userId 维度必须应用层

### CF cookie 不可轻易逆向（重要判断）
Cloudflare 的 `cf_clearance` cookie 背后是：
- JS Challenge（混淆 JS + 指纹检测，随时变）
- TLS 指纹（JA3/JA4，curl/requests 的握手和真 Chrome 不同）
- 行为分析（鼠标轨迹、输入节奏）

**要绕过需用真实浏览器内核（Puppeteer）或指纹浏览器，成本高、慢、资源消耗大。脚本小子做不到。** 这是 CF 防护的核心壁垒，也是"Under Attack + Managed Challenge 能挡住 95% 脚本刷"的根本原因。

### Under Attack 的代价（不能常开）
- 首次访问延迟 1-5 秒（算 JS Challenge）
- 无障碍工具/RSS/原生 App 被误伤
- CF 官方定位是**临时应急模式**，不是常态
- 正确用法：平时不开，被攻击时临时开几小时到几天

## 5. 各层防御职责总表

| 威胁 | nginx 层 | 应用层 | CDN/CF |
|---|---|---|---|
| L4/L7 洪水（>5w rps）| ❌ | ❌ | ✅ 主力 |
| 中等 flood（1k-5w rps）| ✅ 主力 | ❌ | ✅ 补充 |
| 慢连接耗资源 | ✅ limit_conn | ❌ | - |
| 陌生 IP 暴力刷 | ✅ 黑名单 | ✅ 限流 | - |
| 代理池 + 同账号刷 | ❌ | ✅ userId 限流 | - |
| 有效 token 穷举 | ❌ | ✅ 失败熔断 | ❌ |
| 脚本小子（无浏览器）| - | ✅ | ✅ 主力 |
| 已封 IP 持续请求 | ✅ 秒拒 | - | - |

## 6. 博客项目的务实结论

| 目标 | 达成方式 |
|---|---|
| 脚本小子刷不动 | CF 常态防护 + 应用层限流 |
| 黑产不划算 | 应用层 userId 限流 + 失败熔断 + 下沉 nginx（攻击成本递增）|
| 专业团队没兴趣 | 博客本身不值得被针对，CF 免费版兜底 |

**不追求的目标**：防住专业 DDoS 团队（那是云高防的活，博客不值得投入）。

**这套防御匹配威胁等级，是"足够的"而非"绝对的"。**

---

## 7. 各层独立性原则

每一层必须能独立工作，不依赖其他层的存在：

- **应用层**：即使没有 nginx 黑名单下沉，应用层自己也能识别 + 拦截（只是已封 IP 仍会进应用，多消耗一点资源）
- **nginx 层**：即使应用层没下沉黑名单，nginx 自己的 limit_req 也能挡洪水
- **CDN 层**：即使后端全挂，CF 边缘也能挡住大部分攻击

**这样任何一层故障或未部署，整体防御不会归零。** 这也是为什么应用层 P0 三件套必须先补——它是应用层独立工作能力的基础。
