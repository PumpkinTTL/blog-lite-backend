## 为什么有这份文档

经过 R1-R4 四轮代码优化，应用层的业务逻辑、安全契约、性能已基本完整。但**防御层**存在系统性缺陷：

1. **限流取不到真实 IP**（trust proxy 未配）→ nginx 反代后所有请求看起来都是 `127.0.0.1`，IP 维度限流和黑名单全部失效
2. **userId 维度限流没生效**（Guard 顺序错误）→ 已登录用户的限流 tracker 永远走 IP 分支，防不住"登录后刷接口"
3. **Redis 故障 fail-open**（限流挂了就放行）→ 攻击者打爆 Redis 即可绕过全部限流
4. **没有自动封禁**（黑名单纯人工）→ 攻击者刷爆 429 后换个时间窗继续刷，无人自动拦截
5. **黑名单不下沉 nginx**（被封 IP 仍进应用）→ 每个恶意请求仍消耗应用资源，攻击成本不递增

这五点决定了"当前防御挡不住有准备的攻击者"。本文档设计一套**应用层防御闭环**，目标是让恶意行为的识别和拦截成本趋近于零。

## 设计目标：一个完整闭环

```
请求进 nginx
  ├─ 查 shared_dict 黑名单 → 命中 444（0 成本，不进应用）✅
  └─ 未命中 → 转发到应用层
        │
        ▼
   应用层 Guard 链（顺序：鉴权 → 限流 → 黑名单 → 角色）
        ├─ 鉴权 → 挂 req.user（userId）
        ├─ 限流（按 userId 维度，真正生效）
        │   ├─ 正常 → 处理
        │   └─ 超限 → 记录"超限次数"到 Redis
        ├─ 黑名单（IP + userId）
        └─ 业务逻辑中：失败计数 → 达阈值自动拉黑
                          │
                          ▼
                   写 Redis 黑名单 set + TTL
                          │
                          ▼
              nginx 定时拉 Redis → 刷新 shared_dict
                          │
                          ▼
        该 IP/userId 下次请求 → nginx 层直接 444
```

**闭环成立后，恶意 IP 的攻击成本随时间递增**：第一次刷能进应用（被记录），一旦判定恶意，之后所有请求被 nginx 秒拒。

## 核心原则

1. **决策在应用层，执行在 nginx**：业务语义判断（是否恶意）必须应用层做，但封禁的"拒绝"动作尽量下沉到 nginx，让恶意请求不进应用
2. **分层漏斗**：nginx 挡洪水 → 应用层挡慢速刷 → 业务逻辑挡穷举爆破。每层过滤不同的威胁，缺一不可
3. **自动优先，人工兜底**：自动封禁 + 自动解封（TTL），管理员手动黑名单作为补充
4. **匹配威胁等级**：博客项目，目标是"脚本刷不动、黑产不划算、专业团队没兴趣"，不追求绝对防护
5. **不破坏现有业务**：所有改动向后兼容，现有手动黑名单/限流配置继续生效

## 不做什么（明确边界）

- ❌ 不在应用层扛 L4/L7 洪水（那是 nginx + CDN 的活）
- ❌ 不做实时同步黑名单到 nginx（5-10 秒拉一次足够）
- ❌ 不追求防住专业 DDoS 团队（博客不值得，要靠云高防）
- ❌ 不永久封禁任何 IP（IP 会流转，会误伤后续正常用户）
- ❌ 不改变现有 NestJS 架构（不引入新框架，只增强现有模块）
